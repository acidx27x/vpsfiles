# Xray VLESS REALITY VPS Installer and Client Manager

Bash scripts to install and manage an Xray VLESS + REALITY + Vision server on a Debian/Ubuntu VPS.

These scripts are separate from `../wireguard-scripts` and `../amnezia-scripts`. They do not replace or modify either bundle.

## Install

Run on a Debian/Ubuntu VPS:

```bash
cd xray-scripts
sudo ./install.sh
```

The installer uses the official XTLS Xray install script, writes `/usr/local/etc/xray/config.json`, enables BBR-related sysctl settings, opens the public Xray TCP port with UFW, validates the generated config, and starts `xray`.

During installation, the optional next-hop prompt accepts a VLESS URI generated by this bundle's `add-client.sh`. Leave it empty for direct-only operation. Supplying a URI adds an available `next-hop` outbound; clients still use the direct exit unless they are explicitly created or switched with the next-hop route.

When a next hop is configured, the installer can also expose an optional no-auth SOCKS5 listener on `127.0.0.1` for Telemt or another local application. Enter a separate local port to enable it, or leave the prompt empty to disable it.

## Update

```bash
sudo ./update.sh
```

This uses the official Xray updater without rerunning this bundle's installer or changing server configuration, REALITY identity, clients, endpoints, UFW, or sysctl state. It validates the current config with the updated binary. If the service was active, the updater restarts and verifies it, restoring the prior binary if validation or startup fails.

The installed server config starts with an empty VLESS client list. It still contains one generated unused REALITY server shortId because Xray requires `realitySettings.shortIds` to be a non-empty list.

Defaults:

```text
TCP port:       443
Protocol:       VLESS
Flow:           xtls-rprx-vision
Transport:      raw
Security:       reality
Target:         www.firefox.com:443
Server name:    www.firefox.com
Fingerprint:    firefox
Initial clients: none
Routing:        direct by default; optional next hop selected per client
Local SOCKS5:   disabled by default; optional TCP-only next-hop path
```

## Real HTTPS Fallback

Use the separate `../nginx-scripts/install.sh` before installing Xray when this VPS should answer active probes with its own real domain and certificate. The Nginx installer prints values similar to:

```text
REALITY target host:port: 127.0.0.1:8443
REALITY serverName/SNI:   fallback.example.com
```

Enter those values in the existing Xray target and SNI prompts. Nginx listens for TLS only on loopback, so Xray remains the public TCP port 443 listener and forwards unauthenticated REALITY connections to the site.

## Two-hop Setup

Install the exit VPS first. For example, on Amsterdam:

```bash
cd nginx-scripts
sudo ./install.sh

cd ../xray-scripts
sudo ./install.sh
# Leave the next-hop VLESS URI empty.
sudo ./add-client.sh russia-relay
cat clients/russia-relay/vless-russia-relay.txt
```

Copy the resulting one-line URI. Then install the Russian relay:

```bash
cd nginx-scripts
sudo ./install.sh

cd ../xray-scripts
sudo ./install.sh
# Paste the Amsterdam URI into the next-hop VLESS URI prompt.
sudo ./add-client.sh phone
sudo ./add-client.sh --next-hop tablet
```

In this example, `phone` exits directly from Russia while `tablet` exits through Amsterdam. A client routed through Amsterdam is fail-closed: if the `next-hop` outbound is unavailable, Xray does not fall back to the Russian direct exit.

The URI parser intentionally accepts this bundle's VLESS + RAW + REALITY + Vision link format. It rejects incompatible transports or incomplete REALITY credentials before changing the Xray configuration.

## Optional Local SOCKS5 Relay for Telemt

To send Telemt traffic through the exit VPS, install Xray on the exit VPS first, create a client for the entry VPS, and copy its VLESS URI:

```bash
cd xray-scripts
sudo ./install.sh
# Leave the next-hop URI and local SOCKS5 port empty.
sudo ./add-client.sh telemt-vps1
cat clients/telemt-vps1/vless-telemt-vps1.txt
```

On the entry VPS, install Xray and paste that URI at the next-hop prompt. Enter an unused port such as `1080` at the local SOCKS5 prompt:

```bash
cd xray-scripts
sudo ./install.sh
```

The listener is `127.0.0.1:1080`, has no authentication, accepts TCP only, and is not added to UFW. Its routing rule always selects the `next-hop` outbound; it does not fall back to the entry VPS's direct exit when the next hop is unavailable. Public VLESS clients retain the existing per-client direct or next-hop routing behavior.

Finally, install Telemt on the same entry VPS and enter the same local SOCKS5 port. The resulting path is:

```text
Telegram client -> Telemt on VPS1 -> local Xray SOCKS5 -> VLESS/Xray VPS2 -> Telegram DC
```

For unattended Xray installation, pass both settings, for example `sudo XRAY_NEXT_HOP_URI='<vless-uri>' XRAY_LOCAL_SOCKS_PORT=1080 ./install.sh`. `update.sh` preserves the generated Xray configuration.

## Client Commands

After install, the server starts with an empty client list. Create the first client with a unique UUID and REALITY shortId, add it to the server config, and write a VLESS share URI:

```bash
sudo ./add-client.sh phone
```

Create a client routed through the configured next-hop outbound:

```bash
sudo ./add-client.sh --next-hop tablet
```

Create a client config that connects to the server's saved public IPv6 endpoint:

```bash
sudo ./add-client.sh --ipv6-endpoint phone
```

The endpoint and route flags can be combined:

```bash
sudo ./add-client.sh --ipv6-endpoint --next-hop tablet
```

Change an existing client's route without changing its UUID, short ID, or VLESS URI:

```bash
sudo ./set-client-route.sh --next-hop phone
sudo ./set-client-route.sh --direct phone
```

Remove a generated client from the server config and delete its generated files:

```bash
sudo ./remove-client.sh phone
```

Remove Xray data created by this script bundle:

```bash
sudo ./uninstall.sh
```

`uninstall.sh` stops and disables `xray`, removes the generated config, removes generated client files while keeping `clients/.gitkeep`, removes script state files and `install-backups`, removes the Xray BBR sysctl file, and tries to remove the saved Xray TCP UFW rule. It does not uninstall Xray packages or binaries.

## Client Setup

Generated client files are written to `clients/<name>/`:

```text
<name>.uuid
<name>.short-id
vless-<name>.txt
```

Import `vless-<name>.txt` into a VLESS-capable client.

The generated share link uses:

```text
type=raw
security=reality
encryption=none
flow=xtls-rprx-vision
fp=firefox
```

## Notes

Client names may contain only letters, numbers, dot, underscore, and dash.

The scripts keep generated endpoint, IPv6 endpoint, VLESS port, server shortId, SNI, and REALITY key state in files next to the scripts. The server config remains the source of truth for active clients, credentials, and routes, including the optional local SOCKS5 listener.

The next-hop URI is not saved as a separate state file. Its connection fields are stored only in the mode-600 Xray server configuration.

Next-hop client names are stored in the managed routing rule tagged `client-next-hop`. Xray matches these names against the existing VLESS client `email` fields. Private-address and BitTorrent block rules remain before the managed client rule; unmatched clients use the first `direct` outbound.

The scripts do not migrate configurations created by the earlier all-client catch-all next-hop setup. Reinstall or manually remove that catch-all rule before using these per-client commands on such a configuration.
